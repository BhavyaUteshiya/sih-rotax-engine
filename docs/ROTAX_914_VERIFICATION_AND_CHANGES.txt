PHASE 4: SEVERE VIOLATION / HARD-LIMIT DEBOUNCE BYPASS
==================================================

1. ISSUE IDENTIFIED
During the final verification audit, it was discovered that the 2.0-second debounce timer in ResidualAnalyzer suppressed ALL warnings equally, including severe deviations and critical hard-limit violations (e.g. RPM > 5800).

2. RESOLUTION
- Updated src/digital_twin/analysis/residual_analyzer.py to parse physical operating safety limits directly from configs/module02/engines/rotax_914.yaml
- Implemented a severe violation check in ResidualAnalyzer.analyze().
- If an observed value crosses a documented max operating limit (e.g., max_takeoff_rpm = 5800.0, max_safe_cht_k = 408.15K), the warning is flagged immediately (bypassing the 2.0s transient debounce timer).
- Normal threshold excursions (e.g. RPM deviation of 150 but absolute RPM < 5800) continue to use the 2.0s debounce timer.

3. VALIDATION
Created a unit test to validate Conditions A, B, C, and D:
- Condition A: Short transient (1.5s duration) triggers 0 warnings and properly clears tracking state.
- Condition B: Persistent violation (>2.0s) properly triggers warnings after the debounce timer expires.
- Condition C: Severe hard-limit violation (e.g. RPM=5850) triggers the warning instantaneously, bypassing the debounce timer.
- Condition D: Engine 1 and Engine 2 maintain completely independent debounce and tracking states.

4. END OF INTEGRATION
The Rotax 914 Digital Twin Integration is complete.


==================================================
PHASE 5: PARAMETER-SPECIFIC TOLERANCES & DEBOUNCE
==================================================

1. ISSUE IDENTIFIED
The user identified that a universal definition of "major deviation" or a uniform 2.0s debounce timer for all engine parameters is flawed, as different parameters have different scales, limits, and acceptable transient behaviors.

2. RESOLUTION
- Updated `configs/digital_twin_config.yaml` to structurally support parameter-specific tolerances (e.g., `ABSOLUTE` vs `RELATIVE`) and parameter-specific `debounce_sec`. By default, existing absolute values and a 2.0s debounce are preserved to maintain backward compatibility, ensuring calibration requirements are highlighted.
- Updated `ParameterResidual` in `src/digital_twin/models/residual_state.py` to accept `tolerance_type` and compute warnings accurately against absolute residuals or relative percentages.
- Refactored `ResidualAnalyzer.analyze()` in `src/digital_twin/analysis/residual_analyzer.py` to pull parameter-specific tolerances and debounce periods from the configuration, applying them independently per parameter while preserving hard-limit bypass logic.

3. VALIDATION
- Extended validation tests (`test_parameter_debounce.py`) to confirm that different parameters behave correctly according to their specifically assigned debounce periods (e.g. a parameter configured with a 5.0s debounce does not trigger until 5s, while a parameter with a 1.0s debounce triggers earlier).
- Verified previous test suite (`test_hard_limit.py`) remained unbroken and that hard-limits continue to bypass the parameter-specific debounce correctly.

==================================================
PHASE 6: OPERATING LIMITS AND RESIDUAL TOLERANCES
==================================================

1. ISSUE IDENTIFIED
The integration required aligning the residual-tolerance system and safety limits with verified Rotax 914 authoritative data. Previous checks only bypassed debounce for upper limits, ignoring lower physical limits. 

2. AUDIT FINDINGS
- Expected vs Actual Simulation Residual Tolerances: No Rotax authoritative documentation exists specifying simulation residual tolerances. Thus, all 18 parameters remain classified as ESTIMATED and use ABSOLUTE thresholds with a 2.0s debounce.
- Verified physical operating limits from rotax_914.yaml dictate boundaries, not modeling tolerance.

3. RESOLUTION
- Updated ResidualAnalyzer._load_hard_limits() to explicitly parse both max_limits and min_limits (e.g. min_oil_pressure_pa).
- Updated the severe violation bypass check to trigger immediately on both UPPER limits (observed >= max_limit) and LOWER limits (observed <= min_limit).
- Added max_safe_coolant_temp_k parsing logic.
